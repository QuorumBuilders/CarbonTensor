# CarbonTensor project naming

The canonical product name is **CarbonTensor**. Use this capitalization in
backend descriptions, API documentation, and shared project documentation.
The backend's normalized tooling identifier is `carbontensor-backend`.

## Audit and changes

The repository audit on 2026-11-10 was completed before editing. It searched
case-insensitively for `TensorCarbon`, `Tensor Carbon`, and underscore, hyphen,
or whitespace variants, then inspected other names containing `tensor` and
project configuration. It found 20 old-name occurrences in 12 authored files:
11 in seven backend/shared files and nine in five frontend files. Generated
dependencies, build output, and Git history were excluded from source changes.

| Location | Classification | Decision |
| --- | --- | --- |
| Root `README.md` heading | Product branding | Updated to CarbonTensor. The illustrative `awd-carbon-platform/` directory label also becomes `CarbonTensor/`; no real directory is renamed. Line endings were normalized to LF for the repository whitespace check. |
| Root `AGENTS.md` heading, product introduction, and contract display title | Product branding (three occurrences) | Updated the names without changing agent rules or requirements. |
| `backend/AGENTS.md` heading | Product branding | Updated to CarbonTensor. |
| `docs/api/MVP Data Model and API Contract.md` title | Product branding | Updated the display title; the filename and all contract requirements remain unchanged. |
| `backend/pyproject.toml` description | Product branding | Updated to CarbonTensor. |
| `backend/pyproject.toml` project name and its `backend/uv.lock` entry | Technical tooling identifier (two occurrences) | Renamed from `tensorcarbon-backend` to `carbontensor-backend`, with the lockfile regenerated by uv. |
| `backend/.env.example` database and role values | Technical database identifiers (two occurrences) | Retained `DB_NAME=tensorcarbon` and `DB_USER=tensorcarbon`; added a compatibility comment and the current product name. |

Django configuration, app labels, model and field names, migrations, API routes,
authentication code, logging, other backend messages, and the remaining API
documents contained no old product branding. Generic framework labels such as
the `config` project module do not identify the former product name.

## Technical compatibility decisions

The tooling-name change is safe within this repository: `backend/pyproject.toml`
sets `package = false`, and uv records the project as `source = { virtual = "." }`.
The old identifier appeared only in that metadata and its lockfile entry; it is
not an importable Python package. No repository deployment configuration or
other consumer refers to it. The rename changes neither dependencies nor their
versions and does not require a Django migration. Any external automation that
selects the old uv project by name must use `carbontensor-backend` after updating.

Existing PostgreSQL database and role names are independent of product branding.
Changing them would require a separate operational decision covering the actual
database, role privileges, connection settings, and deployed environments. The
example values remain compatible with existing local setups; the environment
variable keys and Django settings are unchanged. This task does not rename or
migrate a database.

Python module paths (`config.*`, `apps.*`), Django app labels, model/field names,
migration identifiers, and `/api/v1/` remain unchanged. The root instructions'
historical `src/tensor/` reference describes the original scaffold, not current
branding. Checkout paths and Git history are not renamed or rewritten.

Old-name mentions in this document intentionally record the audit and
compatibility decisions; they do not specify the current product name.

settings with Django's dummy database backend, without changing application
settings:

  passed. The reviewed lockfile diff only renames and reorders the virtual
  project entry; all dependency versions, sources, and hashes remain unchanged.

  all 83 isolated backend tests, `check` reported no issues, and
  `makemigrations --check --dry-run` reported no changes.
- The repeated source audit found only the documented compatibility values and
  audit-history mentions in the backend/shared scope. The frontend references

- The final diff was reviewed for unintended edits, including confirmation
  that backend runtime code, migrations, and frontend files are unchanged.
  `git diff --check` passed.

because GDAL is unavailable. Database-backed checks and applied migration
